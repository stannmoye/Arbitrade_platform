## Attribution and conflict rules

1. The ownership map above follows the six-window assignment map documented in Window 6's coordination handoff. PR titles and branch labels do not override the assigned window boundaries.
2. PR #278 contains both catalogue/rotation integration and opportunity-generation engine code. The catalogue/rotation contract belongs to Window 1; generation orchestration belongs to Window 3. Window 7 must preserve the code while obtaining Window 3's explicit confirmation and reconciling the branch attribution.
3. PR #283 documents and tests the existing Window 1 catalogue/rotation implementation; it does not add a catalogue table, API endpoint or migration.
4. PR #284 owns the canonical package policy contract. Its shared-file changes to `server/db.ts` must be integrated with Window 3's generation changes and Window 6's aggregate failure reporting.
5. PR #285 owns client-side Trade settings validation and feedback. Its `AdminOperationsPages.tsx` changes must coexist with Window 6's current/historical worker-health UI changes.
6. PR #279's monitoring code reuses the existing worker-health registry. PR #261 is an older-base monitoring branch and is not merged wholesale; only reviewed current-versus-historical behavior is adapted.
7. Shared schema, migration journal, router, worker registration, admin settings and canonical documentation changes require explicit coordination with every affected owner.
8. No implementation window merges directly to `main`; Window 7 owns the final integration PR and merge decision.
